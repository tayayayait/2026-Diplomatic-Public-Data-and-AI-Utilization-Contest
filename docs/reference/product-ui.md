# Product UI Reference

Last reviewed: 2026-06-03

Phase 7 completes the baseline product UI and final responsive/accessibility QA required by `상세서.md`.

## Implemented

- Local itinerary map controls: the departure-location picker now exposes a larger interactive map, explicit map search, recenter, current-location, size-toggle, and Google Maps handoff controls. Touch targets are at least 44px and status feedback is announced through an `aria-live` region. Google Maps core loading is independent from Places Autocomplete, so map/geocoder use can still work when autocomplete is unavailable.
- Local itinerary departure basis: itinerary generation uses the currently entered departure point only. If the user clears the field, the request does not fall back to a previously saved accommodation.
- Local itinerary place links: each generated place card now opens Google Maps with the exact `googleMapsUri` or `googlePlaceId` when available, and otherwise falls back to a combined place-name plus address query instead of address-only search.
- Local itinerary data basis: `/itinerary` calls `generateItineraryFn`, and that server function tries Google-first generation when `GOOGLE_PLACES_API_KEY` and a departure address or coordinates are available. If Google-first generation returns no usable places, the function falls back to Gemini generation.
- Local itinerary recommendation contract: `src/lib/itinerary/recommendation-policy.ts` fixes the default search radius at 3 km, expansion at 5 km, walkable hard cap at 8 km, transit-assisted maximum at 15 km, and scoring weights for preference match, route efficiency, Google popularity, opening-hours fit, budget fit, and category diversity. Candidate collection uses the selected travel mode's hard cap, while scoring still discounts longer distance so famous or high-value farther places can compete. Phase 2 implements candidate collection, scoring, flow-aware route ordering, and Routes API leg timing in the `src/lib/itinerary/google-*` modules.
- Local itinerary intensity fulfillment: the selected itinerary intensity is sent to the server as an explicit target count contract: relaxed 3 places, normal 5 places, and tight 7 places. The same contract now carries food composition: relaxed has 1 restaurant meal and 0 cafe/snack stops, normal has 1 restaurant meal and 1 cafe/snack stop, and tight has 2 restaurant meals and 1 cafe/snack stop. If Gemini-guided Google matching returns fewer places, the server keeps those matches and appends non-duplicate Google-first candidates when available instead of accepting a partial result by default. Google-first replenishment receives the already matched place IDs and names as exclusions, then returns a sequentially renumbered merged itinerary capped at the selected target.
- Local itinerary category balance: Google-first candidate selection now applies intensity-specific meal and cafe caps before route ordering, then fills remaining slots with attractions, culture, nature, shopping, experiences, or other non-food places. Shopping malls and mixed-use facilities such as Canal City Hakata are classified as shopping/experience instead of cafe even when they appear in food-related searches. If a category has no usable candidates, the selector does not fabricate results and fills from remaining candidates while still enforcing food caps.
- Local itinerary day flow: Google-first recommendations now order selected candidates by a start-time-aware travel rhythm before route calls. Morning starts prefer attraction -> meal -> attraction -> cafe/rest -> shopping/experience -> meal, while later starts move the first meal slot forward. Result cards expose stay duration and movement context without expected arrival/departure fields.
- Local itinerary route mode selection: when multiple travel modes are selected, each previous-place-to-next-place leg is requested from Google Routes for the selected modes. Walking is preferred for short legs up to 1.2 km and 20 minutes; otherwise the fastest valid selected mode is used. The chosen leg mode is retained as `recommendationContext.routeTravelMode` and rendered on the card through the existing travel-mode label.
- Local itinerary recommendation reasons: Google-first result descriptions now start with a place-type-specific traveler reason, such as culture/exhibit value for museums, rest value for cafes, local-food fit for restaurants, and shopping/experience value for markets. Timeline cards also expose a visible place-type badge and meal-slot badge when applicable.
- Local itinerary meal slot labels: visible restaurant badges are unified as `식사` by mapping breakfast/lunch/dinner-style meal slots to the generic meal display. Cafe stops use `간식` and the `snack` slot.
- Local itinerary meal exclusion: when the user disables meal inclusion, Google-first generation now skips food-theme search intents and excludes restaurant meal candidates from final selection instead of only hiding meal badges.
- Local itinerary budget sensitivity: Google-first candidate scoring keeps the user-selected budget strategy unchanged. The calculated daily KRW budget and local food/activity allocations are used only as soft price-fit signals for paid restaurants, cafes, attractions, and shopping/experience stops. Famous, highly rated, or otherwise high-value places can outrank cheaper options.
- Local itinerary preference sensitivity: after satisfying the basic daily category mix, Google-first selection now keeps representative candidates from each selected place/food theme when capacity allows, so adding nature, culture, shopping, or cafe preferences can change the final place set instead of only changing explanatory badges.
- Local itinerary regeneration diversity: when the user regenerates an itinerary in the same session, the current result's Google Place IDs and place names are sent as exclusions so the next Google-first candidate pass avoids repeating the same locations when alternatives are available.
- Local itinerary per-day generation: `/itinerary` generates Day 1 from the main generation button, then leaves later Day tabs empty until the user opens that Day and presses `Day N 일정 생성하기`. Each later Day request receives all earlier generated Day place IDs/names as exclusions, so Day 2 avoids Day 1 places, Day 3 avoids Day 1-2 places, and so on. Generated day slots retain the original `ItineraryPlace` payload so each Day tab can render the same rich cards, thumbnails, map markers, and route metadata.
- Local itinerary history persistence: the initial Day 1 generation creates a saved itinerary history record. Later Day tab generation updates that same record with the expanded `places_data` and `days_data`, and histories loaded from the record sheet keep their id so newly generated Days persist back into the selected saved itinerary instead of creating duplicate records.
- Local itinerary history stale-id recovery: if a later Day tab generation tries to update a history id that no longer returns a row from Supabase, `/itinerary` treats that id as stale, clears it, and inserts a new history record instead of failing with a `PGRST116` single-row coercion error.
- Local itinerary history deletion: the history sheet exposes individual delete and "모두 삭제" actions. Both actions require the in-app confirmation dialog, and bulk deletion is limited to the history IDs currently loaded in the sheet.
- Local itinerary recommendation transparency: `/itinerary` shows a recommendation criteria panel with data source, radius policy, sort mode, exclusion rule, and score weights. Google-first result cards also show evidence badges for matched preference, departure distance, rating, review count, opening status, price data, and score when those fields exist.
- Local itinerary recommendation cards: generated place descriptions are shown in full inside the scrollable card list, and long theme labels wrap within the card instead of clipping the recommendation context.
- AI itinerary profile guard: `/itinerary` now blocks generation when no persisted DiploLife profile or destination country exists, and sends the user to `/onboarding` instead of leaving a disabled generator without explanation.
- AI itinerary departure input: `/itinerary` uses the shared Google Maps location input with map search, recentering, current-location, size-toggle, and Google Maps handoff controls. Selected Google Places or Geocoder results preserve latitude/longitude for accommodation storage.
- AI itinerary geocoding boundary: `/itinerary` no longer calls Google REST Geocoding from the browser. Browser-side location resolution uses the Google Maps JavaScript API result already loaded for the input/map experience.
- AI itinerary Google Maps loader: `/itinerary` lazy-loads `APIProvider`, `GoogleMapItinerary`, and the generated itinerary workspace, then wraps the map and departure input in one `APIProvider` with `places` and `geocoding`; the departure input disables its fallback script loader on this screen to avoid duplicate Google Maps JavaScript API loads.
- AI itinerary generation page: `/itinerary` reads the persisted DiploLife `userProfile` and updates accommodation fields through `updateUserProfile`. Gemini itinerary generation is gated by profile country and pending state only; a missing Google Maps key disables map/geocoding enhancements, not the Gemini request itself.
- AI itinerary destination label: `/itinerary` shows the selected destination next to the page title as `선택한 여행지: 국가 · 도시`, converting ISO country codes to Korean display names and using the stored city label.
- AI itinerary first-entry state: completing onboarding reseeds itinerary storage with an empty trip for the selected profile. `/itinerary` restores persisted generated results only when the stored country, city, start date, and end date match the current `userProfile`; stale or unrelated results return to the generator view.
- AI itinerary budget plan: `/itinerary` now places total-trip budget and budget strategy directly above the generation button. The plan derives stay days, daily KRW budget, target currency, and food/transport/activity/accommodation allocation from the living-cost analysis when available, then sends that structured `budgetPlan` into Google-first and Gemini itinerary generation.
- AI itinerary budget strategy: the old "예상 경비 수준" selector is replaced by "절약 우선 / 균형 / 경험 우선". Saving mode filters or excludes high-price Google candidates, balanced mode prefers free/low/moderate price levels, and experience mode allows expensive candidates while still showing price evidence when Google provides it.
- AI itinerary transport policy: active travel modes set the Google-first search radius before candidate collection and are retained in each recommendation context. The result card shows the chosen per-leg route mode together with the previous-place travel time and distance.
- AI itinerary smart defaults: `/itinerary` derives itinerary intensity, budget, food themes, vibe themes, meal inclusion, and start time from the current profile. These defaults are recalculated when profile purpose or preference fields change, without being reset by unrelated accommodation edits.
- AI itinerary accommodation cache: itinerary generation updates accommodation fields through a shared profile patch helper. When a location changes without fresh finite coordinates, stale `accommodationLat`/`accommodationLng` values are cleared; when the same location is saved without geocoding, existing coordinates are preserved.
- AI itinerary map route: `/itinerary` now passes stored accommodation coordinates into `GoogleMapItinerary`, renders the map when only accommodation data exists, and draws route lines only through Google DirectionsRenderer. Straight or dashed polyline fallbacks are not shown; if Google Directions cannot resolve a leg, that leg is left without a line. Stored coordinates are preferred over address geocoding; address geocoding is only used as a fallback.
- AI itinerary map-card selection: selected itinerary cards now render a stronger border, tinted background, ring, and shadow; the visible card number is the same number rendered on the map marker. `GoogleMapItinerary` uses shared marker view models so accommodation is rendered as a distinct lodging marker with a home icon and regular stops use the visit-order marker number. The map also exposes a compact visit-order ribbon and focuses the lower route summary on the selected leg when a card or marker is selected. Selecting a marker scrolls and focuses the matching card.
- AI itinerary map marker fallback: `GoogleMapItinerary` no longer hard-codes `DEMO_MAP_ID`. It reads `VITE_GOOGLE_MAPS_MAP_ID` when configured and falls back to standard Google markers when no real Map ID is available.
- AI itinerary timeline: `/itinerary` renders generated places as an order-sorted timeline with travel segments, Korean meal/category labels, stable Lucide icons, and map selection indices preserved against the original generated place array. The timeline no longer depends on a Google Map context for photo lookups and no longer fabricates fixed arrival/departure or return-travel windows.
- AI itinerary timeline route link: each timeline card's "지도에서 위치 및 경로 보기" action opens Google Maps in a new tab with the trusted place URL or search fallback, while still preserving the in-app place selection state.
- AI itinerary result workspace: generated recommendations now open in a full-width Day-tab workspace instead of staying inside the generator split view. The selected day's places render on the left map with the route path, while the right panel lists only that day's ordered schedule.
- AI itinerary result back action: the generated Day-tab workspace exposes a "세부 설정으로 돌아가기" back button that returns to the itinerary detail settings/generator screen and clears the previously generated result state so old places, routes, and recommendation cards are not shown.
- AI itinerary result cards: generated recommendations are now presented around traveler-facing facts: place name, thumbnail, recommendation reason, Google rating/review evidence when available, estimated cost, previous-place travel mode/minutes, previous-place distance, and a map action that selects the marker and highlighted route segment.
- AI itinerary multi-day editing: generated `/itinerary` results are now synchronized into `itineraryStore` as Day 1 slots using the profile stay-date range. For multi-day profiles, the result panel can switch from map view to the multi-day workspace; the option pool can be dragged into a day timeline without duplicating the same place in that day.
- AI itinerary access and cost integration: AppShell exposes `/itinerary` in desktop and mobile navigation. `/cost` no longer duplicates the itinerary generator; it renders a compact budget handoff CTA to `/itinerary?budgetKrw=...` when a living-cost budget exists.
- Onboarding city search loading: `/onboarding` imports only the country list statically. The large `country-state-city` city dataset is loaded through a dynamic import only when the selected country has no curated major-city list and Step 2 needs fallback city suggestions.
- Home entry screen: `/` now renders a SafeRoute AI first screen with a "서비스 시작하기" CTA that opens `/trips/new`; the desktop hero visual uses `public/home-hero-animation.webp`, generated from `public/홈화면영상.mp4` as a 30fps looping animated WebP.
- Navigation active state: `/trips/new` no longer marks both "새 여행" and "내 여행" as active.
- Dashboard evidence drawer: risk and country evidence rows open a drawer with API ID, API name, field, status, destination, source date, and resolved value.
- Dashboard API status panel: public-data calls are summarized as total, success, warning, and failed.
- Dashboard first result: the main dashboard panel now leads with a consumer-facing "출국 전 안전점검" surface covering official travel alarm, entry conditions, emergency contact, today actions, and evidence-grounded cautions. Gemini wording is no longer the primary frame.
- Dashboard exchange-rate card: the "전일 대비" value is calculated from the latest actual rate and the previous daily actual rate. Missing previous-day data is shown as no rate-change data, not as a mock `0%`.
- Weather risk: the dashboard now includes a "현지 날씨 리스크" panel using Open-Meteo geocoding and daily forecast data. Forecast dates outside the available range are shown as partial or out-of-range, not inferred.
- Exchange-rate timing: `/cost` now includes a reference-only exchange-rate forecast panel. It accepts base currency and target currency, then displays recent actual rates, a 7-day backtested forecast, and the most favorable forecast date. The panel refreshes by the selected travel country/city time zone and bridges the prediction line from the latest actual rate. A simulation modal handles planned amount input and compares today, 1 day, 3 days, and 7 days for that amount in target-currency gain/loss terms. See `docs/reference/exchange-rate-forecast.md`.
- Cost insight freshness: `/cost` now keeps same-day living-cost data stable in local storage. City prices, country cost, and AI budget analysis are reused for the same cache key until the next Asia/Seoul calendar day or the user presses `갱신`; exchange-rate snapshots and forecast results use `fxapi.app` with a 10-minute cache and selected-destination local date key, falling back to the previous CDN source when needed.
- Cost insight fallback: `/cost` resolves both Korean and English supported city names for WhereNext city-price lookups, and retries stale or unsupported static city keys through the official WhereNext city-price index. If the selected country has no item-level city-price dataset, the local price card renders the official country cost-of-living monthly breakdown instead of an empty "city data not found" card. Country-level fallback rows are shown in the selected country's local currency and include a KRW conversion using the stored USD/KRW and local-currency/KRW rates. If Gemini budget analysis is unavailable, already fetched city prices and country cost remain visible, and the page shows a conservative data-based fallback budget/tips panel instead of hiding the local price table and smart tips.
- Local essentials: the dashboard now adds a Google Places-backed "현지 필수 장소" panel for hospitals, pharmacies, and police stations. Missing API keys degrade to explicit Google Maps search-link fallback, not fabricated place data.
- Action plan: the dashboard now shows "오늘의 실행 순서", a deterministic ordered list that combines verified public data, weather risk, local-place links, and unfinished checklist items without asking Gemini to invent new risks.
- Checklist evidence rows: generated checklist items keep their source API and default evidence field, then render the linked public-data source.
- Emergency card sharing: the emergency card exposes print/PDF and guardian-share actions, plus offline/share state badges.
- Guardian share route: `/share/$shareId` renders a 7-day public snapshot for guardians without raw API response snapshots, request params, or uploaded document contents.
- Country life tab: long KOICA life/activity records are summarized into top metrics, short safety notices, and collapsible local-life/activity sections so raw public-data paragraphs do not dominate the page.
- Safety detail route: `/safety` now prioritizes travel alarm status, recent incident summary, and callable emergency contacts, with long public-data text moved into expandable source sections.
- Phase 7 accessibility pass: routed screens expose a single `#main-content` target, global keyboard skip link, labeled desktop/mobile navigation landmarks, and visible current-page navigation state.

## Privacy Boundary

Guardian share snapshots include only summary fields needed for safety coordination:

- trip title, destinations, date range
- risk level, score, and summary
- checklist counts
- emergency contact, phrases, and action steps
- unknowns

The share snapshot deliberately excludes raw `publicData`, `evidences`, `responseSnapshot`, request parameters, and uploaded source files.

## QA Coverage

- Browser E2E coverage now verifies the dashboard evidence drawer, guardian share link creation, public share loading, and exclusion of raw source fields from the public snapshot.
- TanStack Start server functions are protected by CSRF middleware for same-origin RPC requests.
- Home CTA, root responsive checks, touch target size, skip link focus, main-content landmark, and current navigation state are covered by `tests/e2e/saferoute-responsive.spec.ts`.
